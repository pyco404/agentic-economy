# Agentic Economy development and release workflow

- Use `main` for development. Preserve published history, backup branches, original worktrees and unrelated unfinished files. No routine feature branches/PRs, force pushes, resets or history rewrites.
- Use granular Conventional Commits, preferably one file per commit. Routine tested main pushes and production website/API releases are authorized; financial activation is separate.
- The permanent Railway target is **production only**: frontend, backend/API (`ROLE=all`) and its isolated `aeco_production` PostgreSQL. Do not add environments, service splits or approval workflows without demonstrated need.
- Routine release sequence: code → relevant local tests → local/isolated Devnet verification where applicable → production build → explicit pinned-commit Railway production deployment → actual public-domain verification. **Staging deployment/promotion is not a prerequisite.** Documentation-only changes need no application deployment.
- Keep production repository auto-deploy triggers absent. Before a push verify this; promote only the tested application commit explicitly, record frontend/API commit and deployment IDs, and preserve the preceding known-good releases for rollback. Do not change secrets or financial flags as part of code deployment.
- Database migration application is never routine release authorization. Inspect the actual database identity and pending/checksum state before a backend release; stop for separate approval if schema changes are required. Keep the existing approved 001–004 boundary. Never run migrations, restore or copy staging/demo data into production without specific authorization.
- Keep Mainnet token execution, broadcasting, real payments, treasury signing and payouts disabled until separately approved. Initial Mainnet access is restricted server-side to the official deployer. Website deployment does not authorize $AECO creation or unlock public launching.
- Preserve the exact official vanity mint. Never access the owner's mint private key. The owner approved Gamine-style automatic server mint co-signing with an owner-installed, backend-only sealed AECO_VANITY_MINT_SECRET; keep the existing offline fallback. Only the fixed authenticated deployer and exact persisted official launch message may use it; Phantom must separately sign before submission. Never retrieve/dump that secret through API/CLI, print process environments or copy it into AppConfig, logs, Git or frontend artifacts. After finalized official creation verify authorities and remove only this secret without reading it; the special mint path must remain unusable after creation. Do not pre-fill token metadata/artwork or Developer Buy. Developer Buy is off by default for everyone, including $AECO; the user enters an optional SOL budget (up to nine decimals), with an exact 3.5% supply cap. Historical percentage drafts and attempts retain their recorded terms. The earlier 1% preference is withdrawn as a requirement. Vanity mint handling must not restrict or preselect Developer Buy.
- Use the normal Create Coin flow: wallet-owned details persist automatically, and the server binds the exact official mint to one durable launch intent. Do not require Save draft, My Drafts, a user-supplied draft ID or a separate launch wizard. An optional legacy draft restriction may narrow access; it is not required for initial preparation. A valid mint co-signature, separate Phantom approval and existing financial activation gates remain mandatory. Restricted Mainnet launch activation was explicitly approved and verified on 2026-10-23; preserve the live deployer-only flags and official-origin CORS during routine releases. Public launching and payouts remain disabled.
- The owner intentionally has not funded the deployer. Do not request funding or repeat balance checks during infrastructure preparation; check balance only at the owner-initiated final launch authorization stage. Never initiate or schedule a launch automatically.
- Public-demo has been retired with owner approval after an off-platform backup and verified isolated restore. Do not recreate it. Staging remains preserved and is not a release dependency; its services, database, volumes, data, evidence and DNS require a dependency audit, verified backup/restore and separate owner approval before deletion. Do not revoke shared provider credentials when retiring an environment.
- Verify real HTTPS/routes, API/database readiness, native WebSocket, secure origin-bound authentication, desktop/mobile navigation and financial-off capabilities after an application release. Railway Online alone is insufficient.
- The original `codex/frontend` workspace contains preserved unfinished work; do not overwrite it. Continue development in the reviewed `main` worktree.
- Physical Phantom mobile on-chain acceptance remains DEFERRED; do not reopen its gateway or request more tests. Phase 3 stays blocked until the official $AECO launch and required Phase 2 acceptance are independently verified.
