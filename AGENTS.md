- Use `main` for development. Preserve published history, backup branches, original worktrees and unrelated unfinished files. No routine feature branches/PRs, force pushes, resets or history rewrites.
- Use granular Conventional Commits, preferably one file per commit. Routine tested main pushes and production website/API releases are authorized; financial activation is separate.
- The permanent Railway target is **production only**: frontend, backend/API (`ROLE=all`) and its isolated `aeco_production` PostgreSQL. Do not add environments, service splits or approval workflows without demonstrated need.
- Routine release sequence: code → relevant local tests → local/isolated Devnet verification where applicable → production build → explicit pinned-commit Railway production deployment → actual public-domain verification. **Staging deployment/promotion is not a prerequisite.** Documentation-only changes need no application deployment.
- Keep production repository auto-deploy triggers absent. Before a push verify this; promote only the tested application commit explicitly, record frontend/API commit and deployment IDs, and preserve the preceding known-good releases for rollback. Do not change secrets or financial flags as part of code deployment.
- Database migration application is never routine release authorization. Inspect the actual database identity and pending/checksum state before a backend release; stop for separate approval if schema changes are required. Keep the approved 001–005 boundary; migration 005 was separately approved on 2026-10-23 for the market-only trade journal and cursors after a verified production backup/restore.
