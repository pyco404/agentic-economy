# Observable authoritative agent work

## Audit and scope

The backend already implements utility-based task planning, permission validation, cached BFS road/bridge/plaza navigation, reserved goods pickup, delivery, timed production shifts and repairs, escrow settlement, and hash-chained verified receipts. Production can run without an agent; old unclaimed deliveries may be completed by background city labour without individual agent points. The client must not attribute those operations to a visible agent.

This feature projects that existing state into the world. It adds no commands, economic rules, persistence fields, migrations, blockchain activity, wallet permissions or real payouts. Individual planting, harvesting, kneading and passenger/cargo animations are not separate economic operations. Procedural work poses represent the registered production shift or repair; they do not mint resources or settle rewards. The decision planner remains the existing deterministic utility planner, not a newly added LLM service.

## Compatible wire changes

- `AgentSummary.work` is optional. New servers include its source tick, complete current task, current-leg destination building and entrance, navigation target, remaining work ticks and actual cargo. No assignment means `task: null` and `destination: null`.
- Existing `world.snapshot` and `GET /api/v1/world/agents` automatically carry the enriched summaries. Agent details inherit them.
- `agent.moved.moves[].agent` optionally contains the same-tick full summary, including authoritative Credits, verified-task count and contribution points. Working-in-place agents continue receiving updates. Old messages without this field remain valid.
- HTTP refresh recovers global assignments and latest receipts; newer stream data wins over delayed reads. Browser restarts read the current backend position and assignment, rather than generating a new identity or task.
- Existing task/receipt endpoints remain authoritative. Latest-page receipts are explicitly labelled as recent; cumulative counters come from the backend agent, not the receipt page length. Active assignments are merged into the displayed task queue without duplicating task IDs.
- The generated OpenAPI schema was updated; old optional-field fixtures remain compatible.

## Presentation

Road/bridge/plaza interpolation reuses the existing pedestrian graph and sidewalk presentation. Large sample gaps recover along connected paths at the current two-cells-per-tick pacing. Unknown/disconnected routes hold their last position rather than crossing buildings/water or teleporting. Positions persist in the mounted City runtime across React updates and page overlays. A lagging visual agent does not perform a workplace pose before reaching the authoritative entrance.

Cargo is shown only for nonempty backend cargo. Farm, mill, bakery, warehouse/workshop and maintenance poses reuse the existing instanced citizen body/arms. No particles, extra citizen meshes, physical deliveries or economic events are generated by those poses. Work telemetry is sampled four times per second; work metadata increases existing stream payloads rather than opening per-agent subscriptions.

Economy shows current assignments, named workplaces, assigned agents, task Credit budgets, potential points, and actual receipt awards/checks where available. Production-stage controls use the authoritative building catalog's outputs, and market buildings for resident demand; they highlight registered facilities with one shared instanced ring batch. View-in-city actions use the existing building inspector and camera focus. Agent Studio/World inspectors show the same canonical identity, job, destination, preferences, receipt evidence and earnings. Follow Agent smoothly tracks the existing rendered position beside the inspector; mouse/touch orbit/pan, rotate/reset buttons, selection changes and disappearance of the agent safely release following.

Traffic remains ambient presentation, and server navigation remains the existing road/bridge/plaza grid. This feature does not introduce pedestrian/vehicle physics, a new logistics economy, LLM planning, or per-operation farm machinery simulations. On unsupported older servers assignment details remain unavailable rather than invented.

## Railway publication gate

Read-only Railway inspection confirms production service `heartfelt-wisdom` still has GitHub source branch `main`. Its last deployment failed and there are no active deployments, but pushing main cannot be assumed harmless. Staging frontend tracks `codex/frontend`; staging API tracks `staging` and has a pre-deploy migration command. Existing main also includes identity migration 003, outside this feature; deploying this baseline must not silently apply it to staging.

Prepare one-file Conventional Commits locally. Do not push main while it may trigger an unapproved production deployment; do not change Railway source settings or run migrations without approval. Staging must receive a coordinated compatible backend/frontend release after its migration baseline is explicitly reviewed. The new fields alone are backward compatible but older staging does not provide the new work presentation.

### Final results

- 70 backend tests passed (69 in the complete suite plus the added stationary-progress integration case); 15 PostgreSQL-dependent cases were skipped, with no database target supplied.
- 24 shared-contract/fixture tests, 136 frontend unit tests, and seven world-generation tests passed. The full frontend rerun passed with one worker and a 60-second test timeout.
- All three work browser scenarios passed: a real surface travel/work/receipt cycle, and workplace discovery at 390px and 768px. Workspace typecheck, root lint, backend/shared/frontend builds and generated OpenAPI check passed.
- Like-for-like local 1440×1000 native-GPU sampling: baseline median 22.0 ms / p95 126.4 ms; feature median 21.8 ms / p95 123.4 ms. Both rendered 413 buildings with 393 draw calls; about 31 frames/s over ten seconds. Existing periodic frame spikes remain; this is one local comparison, not a physical-device or broad performance certification.
- Staging frontend and API both returned HTTP 200; API reported demo mode with financial features disabled. No settings, deployments or migrations were changed.

Staging's migration table was inspected read-only and contains only `001_init.sql`, `002_coordination.sql`, and `004_launchpad_workspace.sql`; identity migration 003 is not applied. The deployed Phase 2 workspace checkpoint also has commits outside this main baseline, so the complete release must reconcile that work rather than replacing staging with a partial main snapshot. No such integration, migration or deployment was attempted here.
